# Security policy

## Reporting a vulnerability

Do not open a public issue for a security problem. Open a private security
advisory at
<https://github.com/jawaracloud/skopos/security/advisories/new>. The repository
is public, so any GitHub user can use the advisory form. If the form is
unavailable, open a minimal public issue that asks the maintainers for a
private channel, without disclosing the vulnerability details. Include the
affected version or commit, a reproduction, and the impact.

## Response targets

The maintainers aim to acknowledge a vulnerability report within 7 days and
provide an initial assessment within 14 days. These are targets, not a
guarantee. Disclosure is coordinated with the reporter; the default target is
90 days after the initial report, or sooner when a fix and advisory are ready.

## Supported versions

Only the latest alpha release is supported. Alpha releases have no compatibility
guarantee and may receive security fixes only on the latest tag. The
`skopos-0.1.0-alpha.1` chart release predates the supply-chain release process
and is kept for historical reference only; it is not covered by the signing and
provenance guarantees below.

## Security model for v0.1

- **Optional Basic authentication.** `auth.enabled=true` protects the query and
  version routes with one operator-managed username/password; `/healthz` and
  `/readyz` stay open for Kubernetes probes. There is no per-user
  authorization, tenant isolation, or audit identity. Basic auth is only safe
  over TLS. Disabled by default; do not expose the gateway without either the
  chart auth or an authenticating proxy.
- **ClusterIP only.** The gateway, Collector, and ClickHouse services are
  ClusterIP. NetworkPolicies restrict ingress traffic between components (v0.1
  does not ship egress policies; that is M6 hardening). The chart does not
  expose the gateway to the internet.
- **Read-only ClickHouse user.** The gateway connects with a ClickHouse user
  that has `SELECT` on the configured database and `readonly = 2` (read-only
  queries, but query settings can be changed to enforce limits). Query time,
  memory, rows read, and result rows are bounded.
- **Parameterized SQL.** User values are passed to ClickHouse as query
  parameters. Identifiers come from whitelists. The SQL emitter has a fuzz test
  that asserts user values do not appear as SQL literals.
- **OBI privileges.** OBI runs as a DaemonSet with the smallest capability set
  that matches the enabled features. The default chart excludes network
  observability and trace-context propagation, so it does not grant
  `CAP_NET_ADMIN` or `CAP_SYS_ADMIN`. See `values.yaml` and OBI's security
  documentation before enabling those features.
- **Supply chain.** Go modules use `go.sum` and a committed `vendor/` tree.
  Third-party images are pinned by digest, GitHub Actions are pinned by commit
  SHA, and the registry enforces SHA pinning. Releases are built from an
  annotated tag whose commit is on `main`; images and charts are signed with
  keyless Sigstore, SBOMs and build provenance are attested, and GitHub releases
  are immutable. There are no long-lived signing keys. See
  [docs/security/supply-chain.md](docs/security/supply-chain.md).

## Review status

The SQL emitter and escaping, Helm `securityContext` and capabilities, and
NetworkPolicies have automated tests, fuzzing, and a human review gate in
CONTRIBUTING.md. They have not yet had an independent human security review.
The alpha is not a substitute for that review; treat it accordingly.

## Known limitations

- The gateway trusts its own network. Do not expose it directly to the internet.
- ClickHouse credentials are generated by Helm and stored in a Kubernetes
  Secret. The default chart does not enable encryption at rest or TLS between
  components. Use your platform's secret management and a service mesh or
  network controls if your threat model requires them.
- The OBI DaemonSet needs `hostPID` and host mounts. Treat it as a privileged
  node-level agent, even when running with capabilities instead of
  `privileged: true`.
- OBI capability sufficiency is distribution-dependent. The real e2e harness
  uses `privileged: true` because this host's container runtime/kernel policy
  blocks some netns iterators even with the chart's capability set and
  `seccomp=unconfined`. The capability-only path still produced HTTP
  spans/metrics in testing, but validate it on your node runtime before
  treating the chart's default as equivalent to privileged mode.
- The alpha query APIs are implemented with narrow, published support lists.
  Do not put production data behind a gateway whose query semantics have not
  passed the beta compliance gates.
